# Chaos Panel: дизайн и техническое задание

Дата: 2026-09-17. Статус: принят, основа для плана реализации.

## 1. Цель

Публичный сайт-стенд, на котором посетитель видит схему распределённой системы,
может вывести из строя любой её компонент кнопкой «Сломать», наблюдает каскад
последствий на схеме и в Grafana, и может сам воспользоваться этой системой
как обычный пользователь, чтобы столкнуться со сбоем на своём заказе.

Система должна быть настоящей: реальные Kafka, Redis, Postgres, gRPC и HTTP
между сервисами, балансировщик перед репликами. Сбои тоже настоящие:
остановка и заморозка контейнеров, позже сетевые задержки и потери.

### Не цели

- Изоляция посетителей друг от друга. Мир один, общий (решение принято).
- Kubernetes. Целевая платформа: один хост с Docker Compose.
- Полнота предметной области. Домен нужен только как повод для взаимодействий.

## 2. Предметная область

Доставка еды. Пользователь смотрит меню, собирает заказ и следит за статусом:

`accepted → paid → cooking → cooked → delivering → delivered`

Каждая стадия принадлежит своему компоненту и своему типу взаимодействия,
поэтому падение любого компонента даёт различимый, объяснимый эффект:

| Стадия | Кто | Взаимодействие | Эффект сбоя для пользователя |
|---|---|---|---|
| меню | order-svc + Redis | gRPC, cache-aside | Redis упал: меню грузится дольше, но работает (деградация) |
| accepted | gateway → order-svc → Postgres | HTTP → gRPC → SQL, синхронно | ошибка сразу при создании заказа |
| paid | payment-svc (фаза 2) | gRPC с таймаутом и circuit breaker | заказ отклонён или задержан |
| cooking/cooked | kitchen-svc | Kafka, асинхронно | заказ принят, но «завис»; после починки очередь рассасывается |
| delivering/delivered | courier-svc (фаза 2) | Kafka, асинхронно | то же на следующем шаге |

## 3. Архитектура

Две плоскости, физически разделённые:

- **Демонстрируемая система** (data plane): сервисы доставки еды.
- **Плоскость управления** (control plane): `chaos-controller`, наблюдаемость,
  генератор нагрузки. Она наблюдает за data plane и ломает её, но не участвует
  в бизнес-потоке.

### 3.1 Топология MVP

```
                 ┌──────── traefik (LB) ────────┐
   пользователь ─┤                              │
                 └─► gateway-1 ──┐   gateway-2 ◄┘
                                 │ gRPC
                                 ▼
                             order-svc ──SQL──► postgres
                                 │  ▲    └─cache─► redis
                        produce  │  │ consume
                                 ▼  │
                               kafka (orders.created / orders.cooked)
                                 │  ▲
                         consume ▼  │ produce
                             kitchen-svc
```

Плоскость управления: `chaos-controller`, `loadgen`, `prometheus`, `grafana`,
`kafka-exporter`, `docker-socket-proxy`.

### 3.2 Компоненты data plane

| Сервис | Стек | Ответственность |
|---|---|---|
| traefik | Traefik | балансировка на 2 реплики gateway, health-check реплик |
| gateway | Rust, axum | REST для клиентского приложения, SSE статуса заказа, вызовы order-svc по gRPC |
| order-svc | Rust, tonic, sqlx, redis | меню (Postgres + Redis cache-aside), создание заказа, публикация `orders.created`, консьюмер `orders.cooked`, обновление статуса |
| kitchen-svc | Rust, rdkafka | консьюмер `orders.created`, имитация готовки 5–15 с, публикация `orders.cooked` |
| postgres | Postgres 17 | меню, заказы |
| redis | Redis 7 | кеш меню |
| kafka | Kafka 3.x KRaft, один брокер | топики `orders.created`, `orders.cooked` |

Фаза 2 добавляет `payment-svc` (gRPC, circuit breaker), `courier-svc`
(Kafka) и `analytics-svc` → ClickHouse как вторую, колоночную БД.

### 3.3 Компоненты control plane

| Сервис | Ответственность |
|---|---|
| chaos-controller | граф топологии, исполнение сбоев, авто-восстановление, расчёт состояний, поток RPS по рёбрам, SSE в браузер, раздача фронтенда |
| loadgen | N виртуальных пользователей, которые постоянно заказывают еду; источник «жизни» и счётчика людей на схеме |
| prometheus | сбор метрик всех сервисов и экспортеров |
| grafana | анонимный Viewer, provisioned-дашборды; ссылка с каждого компонента схемы ведёт на его дашборд |
| kafka-exporter | лаг консьюмер-групп, чтобы «зависшая очередь» была видна в метриках |
| docker-socket-proxy | единственный путь к Docker API, allowlist только на контейнеры (list, inspect, start, stop, pause, unpause) |

### 3.4 Единый источник правды: `topology.json`

Файл описывает узлы и рёбра. Его читают и chaos-controller (граф зависимостей,
имена контейнеров, ссылки на дашборды), и фронтенд (раскладка схемы).
Дублирования знаний о системе в двух местах быть не должно.

```json
{
  "nodes": [
    {"id": "kitchen-svc", "label": "Kitchen", "kind": "service",
     "container": "kitchen-svc", "pos": {"x": 640, "y": 420},
     "grafana": "kitchen", "faults": ["stop", "pause"]}
  ],
  "edges": [
    {"from": "gateway", "to": "order-svc", "proto": "grpc", "dep": "hard"},
    {"from": "order-svc", "to": "redis", "proto": "redis", "dep": "soft"},
    {"from": "order-svc", "to": "kafka", "proto": "kafka", "dep": "hard"},
    {"from": "kafka", "to": "kitchen-svc", "proto": "kafka", "dep": "hard"}
  ]
}
```

Ребро всегда описывает направление потока данных: по нему фронтенд гонит
частицы. Зависимость выводится из ребра по правилу типа: для `http`, `grpc`,
`sql`, `redis` узел `from` зависит от `to`; для `kafka` оба конца ребра
зависят от брокера, а друг от друга не зависят. `dep: hard` означает
«без этого не работаю», `soft` означает «работаю хуже» (см. 4.2).

## 4. Модель сбоев и состояний

### 4.1 Каталог сбоев

| Вид | Механизм | Что демонстрирует | Фаза |
|---|---|---|---|
| stop | `docker stop` контейнера | connection refused, отказ | 1 |
| pause | `docker pause` (SIGSTOP) | зависание, таймауты, а не ошибки сразу | 1 |
| kill-replica | stop одной реплики gateway | балансировщик, failover | 1 |
| latency | `tc netem delay` внутри контейнера | медленная сеть, деградация | 2 |
| loss | `tc netem loss` | ретраи, флапы | 2 |
| app-error | флаг в сервисе: доля ошибок | circuit breaker | 2 |
| disk-full / oom | лимиты cgroup | ресурсные инциденты | 3 |

Все сбои обратимы и имеют TTL. Контроллер хранит активные сбои в памяти и
при старте (или рестарте) первым делом снимает всё, что мог оставить
предыдущий процесс: проверяет контейнеры из топологии и запускает или
размораживает остановленные. Это защита от «застрявшего» стенда.

### 4.2 Состояния компонентов

- `healthy`: контейнер running, health-check зелёный, активного сбоя нет.
- `broken` (красный): активный сбой на этом узле, либо health-check упал сам.
- `degraded` (жёлтый): узел здоров, но по графу зависит (транзитивно) от
  `broken`. Через `soft`-ребро транзитивность не распространяется дальше
  одного шага: order-svc без Redis жёлтый, но gateway от этого не желтеет.
- `recovering`: сбой снят, контейнер поднимается, health-check ещё не зелёный.

В MVP жёлтый цвет выводится из статического графа. В фазе 2 добавляется
второй источник: ошибки и латентность из Prometheus, чтобы схема показывала
реальную деградацию, а не предсказанную.

Для Kafka-рёбер зависимость: и продюсер, и консьюмер зависят от брокера
(`hard`). Падение консьюмера продюсера не ломает: заказы копятся в топике,
это и есть асинхронность, которую нужно показать.

### 4.3 Правила публичного стенда

- Одновременно активен один сбой. Кнопки других узлов показывают
  «занято, осталось N с».
- TTL сбоя по умолчанию 60 с, после снятия глобальный cooldown 15 с.
- Лимит на IP: не чаще одного сбоя в 2 минуты. Админ-токен снимает лимиты
  и позволяет несколько сбоев одновременно.
- Контроллер сам следит за здоровьем стенда: если после снятия сбоя
  компонент не поднялся за 120 с, форсирует `docker start` и пишет алерт.

## 5. Потоки данных и «жизнь»

- `loadgen` держит N виртуальных пользователей (по умолчанию 20). Каждый
  циклично: меню → заказ → ожидание `delivered` по SSE или таймаут → пауза.
- Каждый сервис отдаёт Prometheus-метрики. Обязательная метрика для схемы:
  `edge_requests_total{src, dst, proto, outcome}`. По ней контроллер раз в
  2 с считает RPS каждого ребра и отдаёт фронтенду.
- Счётчик людей на схеме = активные виртуальные пользователи + активные
  реальные SSE-подключения на gateway.
- Фронтенд рисует поток частицами вдоль ребра: количество и скорость
  пропорциональны RPS, красные частицы для `outcome=error`.

## 6. Фронтенд

Svelte 5 + TypeScript + Vite, статическая сборка вшивается в бинарь
chaos-controller через `rust-embed`. Никакого рантайма на Node в проде.

Страницы:

- `/` панель: SVG-схема из `topology.json`, у каждого узла состояние,
  кнопка «Сломать» (с выбором вида сбоя), ссылка в Grafana. Сверху: людей
  онлайн, заказов в минуту, активный сбой с таймером.
- `/order` клиентское приложение: меню, корзина, «Заказать», таймлайн
  статусов по SSE. Когда что-то сломано, пользователь видит это здесь:
  ошибку, зависание или медленную загрузку.

Визуальный язык: чёрно-белый, цвет только у состояний (жёлтый, красный) и у
потока ошибок. Анимации на CSS/requestAnimationFrame, без тяжёлых библиотек.

Транспорт: SSE `/api/stream` со снимком состояния раз в секунду. Проще и
надёжнее WebSocket для однонаправленного потока, переживает реконнекты.

## 7. API chaos-controller

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/topology` | узлы, рёбра, доступные сбои |
| GET | `/api/state` | текущий снимок: состояния узлов, RPS рёбер, активный сбой, счётчики |
| GET | `/api/stream` | SSE тех же снимков раз в секунду |
| POST | `/api/faults` | `{node, kind, ttl_s?}` → 201 или 409 (занято) / 429 (лимит) |
| DELETE | `/api/faults/{id}` | снять досрочно |
| GET | `/healthz`, `/metrics` | стандарт |

## 8. Наблюдаемость

Prometheus скрейпит все сервисы, traefik, kafka-exporter. Grafana с
анонимным Viewer и provisioned-дашбордами: один дашборд «Overview» и по
одному на класс компонента с переменной `service`. Ссылка из схемы:
`/grafana/d/<uid>?var-service=<id>`. В фазе 2: Tempo, trace-id в ответах
gateway и ссылка «посмотреть трейс заказа».

## 9. Репозиторий и деплой

```
Cargo.toml              workspace
crates/common           метрики, трейсинг, конфиг, health, edge-метрики
crates/proto            .proto + tonic-build
services/gateway
services/order-svc
services/kitchen-svc
services/loadgen
control/chaos-controller
web/                    Svelte-приложение
deploy/compose.yaml     база (образы, сети, healthchecks)
deploy/compose.dev.yaml порты наружу, hot-reload не нужен
deploy/compose.prod.yaml Caddy c TLS, restart: always, лимиты ресурсов
deploy/prometheus/, deploy/grafana/
deploy/ansible/         playbook: docker на VPS, деплой compose, .env
topology.json
Makefile                build, up, down, smoke, test
```

Один Dockerfile для всех Rust-сервисов (multi-stage, `cargo chef` для кеша
зависимостей, аргумент `BIN`). Локально: `make up`. На сервер: `ansible-playbook
deploy/ansible/site.yml -i inventory` с одним хостом. Секреты через `.env`,
пример в `.env.example`.

Бюджет памяти на хосте 8 ГБ: Kafka с heap 512 МБ, Postgres 128 МБ shared
buffers, остальное укладывается в ~2 ГБ суммарно.

## 10. Тестирование

- Unit: расчёт состояний по графу, TTL и блокировки сбоев, лимиты; парсинг
  `topology.json`; логика статусов заказа в order-svc.
- Integration (Rust, `#[ignore]`, запускаются `make smoke` на поднятом
  стенде): заказ проходит все стадии; после `stop kitchen-svc` новый заказ
  застревает на `accepted`, kitchen красный, order-svc и gateway не краснеют,
  а после TTL заказ доезжает; после `stop redis` меню отдаётся, order-svc
  жёлтый.
- Frontend: `svelte-check` и сборка в CI, unit на мапперы состояния.
- CI: GitHub Actions: cargo fmt/clippy/test, сборка образов, smoke на
  compose.

## 12. Риски и решения

- **rdkafka требует librdkafka и cmake в сборке.** Принято: сборка в
  Docker, `cargo chef` кеширует. Альтернатива `rskafka` без consumer groups
  не даёт лага в kafka-exporter, поэтому отклонена.
- **Docker-сокет у публичного сервиса.** Только через docker-socket-proxy с
  allowlist; контроллер работает только с контейнерами из `topology.json`.
- **Общий мир и вандализм.** Один сбой за раз, TTL, cooldown, лимит на IP,
  самовосстановление. Фаза 3 добавляет ночной полный пересоздание стенда.
- **8 ГБ на хосте.** Лимиты памяти в compose, Kafka в KRaft с малым heap,
  ClickHouse только в фазе 2 и опционально.
